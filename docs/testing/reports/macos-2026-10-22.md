The guide says the dev-build E2E has "both spec files". There are now three: `extensions`, `launch` and `sidebar`. `extensions.spec.ts` doesn't call `failOnMainErrors()`, so an error in main during the extension tests wouldn't fail them.

### E2E failure: folders drag (not macOS-only, not fixed here)

`sidebar.spec.ts:105` *folders: made around a tab, dragged into, …* fails on every run here: 2 full runs, plus 3 of 3 on its own. The error is `Pinned` has 2 rows instead of 3 after *Second page* is dragged into the new folder (line 136).

- **Cause:** a race in the test.
  - "New folder" moves *Third page* into Pinned, so the Today rows below it spring to new places. Logged every 100 ms, *Second page* went 208 → 256 → 263 → 237 → 232 px and settled after about 700 ms.
  - `drag()` reads the row's box mid-glide, so the drag starts in the wrong place.
  - Waiting for the row to settle makes the drag land.
- **Not macOS-only:** CI run 39885636739 on `main` failed the same assertion on Windows arm64. CI's macOS runners pass it, presumably because they're slower.
- **`agent/ci-green` already targets this** with `settledBox()` (`ff9520b`), but that fails 3 of 3 here.
  - `expect.poll` calls its function immediately, so the first comparison is between two reads taken milliseconds apart, usually in the same frame. They match, and a moving row counts as settled.
  - Starting with `let last = null` (so the first poll can't pass) made the test pass 5 of 5 here.
  - I left this to the `agent/ci-green` branch rather than open a competing one.

Also: the only one skipped is `launch.spec.ts:272`, the keyboard routing test. That's by design on macOS, where injected keys carry no NSEvent, so by-hand item 3 covers it. CI's macOS runners fail `launch.spec.ts:1245` (*the archive …*) on `main`, but it passed in both runs here.

### Packaged tests on a real Mac: the keychain prompt (macOS-only, fixed)

The `chord-mac-arm64` artifact from Release run 39885476535 (built from `bf1e20b`) failed both smoke tests. Its tabs never loaded and no request reached the test server, even though the same code built locally passed. The `app.asar` files are byte-identical; only the ad-hoc signatures differ.

- **Cause:** cookie encryption keeps its key in the login keychain item *Chord Safe Storage*, and that item trusts only the signature (cdhash) that created it.
  - The earlier local `package:dir` run created it. securityd then logged `ACL partition mismatch: client cdhash:0787… ACL cdhash:3318…` and showed a keychain prompt for the CI build.
  - Chromium loads no page until the prompt is answered.
  - Every build has a new ad-hoc cdhash: `Info.plist` carries the asar's integrity hash, so any code change produces a new one. So on a Mac, `test:packaged` stops on this prompt whenever the build under test isn't the one that last saved the key.
  - CI never sees it, because each runner starts with an empty keychain.
- **Fix:** `mac/fix-packaged-keychain` (`37ae1de`).
  - Packaged launches on macOS pass `--use-mock-keychain`, so the tests never read or write the tester's keychain.
  - A probe confirmed Electron 45 honors the switch: a cookie saved under the real key can't be read under the mock one.
  - A new macOS-only test launches the build, then a re-signed copy (the next build, as the keychain sees it), and requires both to load a page.
  - With the fix, `test:packaged` passes 3 of 3 against both the local build and the CI artifact, and securityd shows no keychain prompts.
  - I didn't run the new test without the fix, to avoid putting another prompt on screen. The failing runs above are that case.
