# S18: agents use Chord through Chord's own MCP server (M0 spike)

**Result: pass on Windows 11 with Claude Code 2.1.328 end to end.** Codex 0.160.1 connects, sends `initialize` and `tools/list`, but no live turn ran: the test account is at its usage limit until Dec 16, 2026. Linux sockets were checked in WSL (Ubuntu, Node 24, Electron 45.3.2). macOS and the Flatpak are planned for CI or checked by hand (below).

**Release builds:** on since 0.14.0 (2026-11-22): `AGENTS_RELEASED` (packages/core/src/agent-tools.ts) is true. For 0.13.1 (2026-11-21) Agents was hidden in packaged builds, while slice (e)'s consent fixes landed. The branches that hid it are gone (#291, #339): the switch now gates only `agentsServe`'s default, kept as the release-switch pattern unreleased switches use.

**Decision (for M1):**

- **Transport.** The running Chord serves a local endpoint and opens no port (D9). On Windows it's a named pipe with a random name; on macOS and Linux, a Unix socket in a new 0700 folder under `$XDG_RUNTIME_DIR` (Linux), the per-user `$TMPDIR` (macOS), or `$XDG_RUNTIME_DIR/app/$FLATPAK_ID/` (Flatpak). The name and a random 32-byte token go in `agent-endpoint.json` in the profile folder. A connection must send the token first. Until it does, Chord writes nothing, and it hangs up after 2 s.
- **`chord mcp`.** It's Chord's own executable, branching on argv as the first thing its main runs. There's no separate script: the RunAsNode fuse stays off, and Chord ships no other runtime. The branch is a stateless relay. It answers `initialize` and `tools/list` itself (the list ships with the build), and connects to Chord only on the first `tools/call`. An agent session that never uses Chord never reaches Chord, and Chord does nothing until a call arrives.
- **Chord not running.** `chord mcp` never starts Chord. A call answers *Chord isn't open. Ask the user to open Chord, then call this tool again.*, and the next call tries again, so the agent needn't restart.
- **Approvals** block inside `tools/call` for at most 45 s. After that the call answers *Waiting for the user…* and the card stays up, so a client's own timeout never fires (Codex's is 60 s). A whole call answers within `CALL_WAIT_MS` (50 s); a step's Send data card still up then is handed over: the call says the step ran and what it sent waits (`sending`), the card stays up as before, and the outcome comes with the agent's next result (`later`; #143, below).
- **The connect card** names the client by its self-reported `clientInfo.title`. It adds the program that started `chord mcp` as a hint, never as proof (§3).

### 1. Transport

| Question | Seen |
|---|---|
| Can Chord's main serve a named pipe? | Yes, with `net.createServer().listen('\\\\.\\pipe\\chord-agent-<16 hex>')`, in plain Node and in Electron's main. |
| The pipe's default DACL (libuv passes no security attributes) | `O:<user> D:(A;;FA;;;SY)(A;;FA;;;BA)(A;;FA;;;<user>)(A;;FR;;;WD)(A;;FR;;;AN)`: full control for SYSTEM, Administrators and the user; **read for Everyone and Anonymous**. Node can't change it. `readableAll`/`writableAll` only widen it. |
| What does Everyone's read grant allow? (`pipe-acl.ps1`) | It can open an instance (`FILE_GENERIC_READ`), but `WriteFile` fails with 5 (access denied), so it can never send the token. After 2.5 s it has 0 bytes, and the endpoint has hung up (109). Each client gets its own instance, so no one reads another's traffic. The worst it can do is hold instances open for 2 s each. |
| Can the DACL be tightened after `listen`? | Yes. The owner opens the pipe with `WRITE_DAC` and calls `SetSecurityInfo`, and later instances keep the new DACL (`D:P(A;;FA;;;SY)(A;;FA;;;<user>)`). That needs a Win32 call: the C# helper Chord already builds with Windows' csc (`build-window-owner.mjs`), or a native addon. **Not needed for M1** (above); a hardening follow-up. |
| Another user, read-only, through the endpoint file | The file inherits `%LOCALAPPDATA%`'s ACL. ⚠ On this machine, that ACL includes **`CodexSandboxUsers:(RX)`**, added by Codex's Windows sandbox. Commands Codex runs in its sandbox can read the token. They still can't write to the pipe (Everyone has read only), so **the pipe's owner-only write is the lock on Windows, and the token is the second one**. M1 must never pass `writableAll`. |
| Squatting the name | A second `listen` on the same name fails with `EADDRINUSE` (libuv uses `FILE_FLAG_FIRST_PIPE_INSTANCE`). The name is random per launch and lives only in the user's endpoint file. |
| Remote clients | libuv doesn't set `PIPE_REJECT_REMOTE_CLIENTS`. `\\localhost\pipe\…` connects, but SMB loopback reuses the local logon (a NETWORK deny ACE didn't block it either), so it shows nothing about a real remote client. A remote client would also need the user's SMB credentials and the token. **Check by hand** from a second machine. |
| Another session, same user | `\\.\pipe\` isn't per-session, so a process of the same user in another session can connect with the token. Same user, same trust: that's intended. |
| Linux socket, another user (WSL, `posix-check.sh`, `nobody` via `setpriv`) | The folder is `drwx------` and the socket `srwxr-xr-x`. `nobody` gets `EACCES` connecting, `EACCES` even with the folder opened to 755 (connecting needs write on the socket), and *Permission denied* reading the 0600 endpoint file. |
| A bad or missing token (Windows and Linux) | The endpoint sends nothing and closes. |
| Flatpak | Not run here. `flatpak/…yml`'s `chord.sh` already points `TMPDIR` at `$XDG_RUNTIME_DIR/app/$FLATPAK_ID` so that every instance finds the running one's singleton socket. The endpoint uses the same folder, so `flatpak run io.github.anaremore.chord-browser mcp` (a second sandbox instance) reaches it the same way. stdio passes through `flatpak run`. **Check by hand** (below). |
| Single-instance lock | The `mcp` branch never calls `requestSingleInstanceLock`. With the Electron host holding the lock, the bridge ran, and the host saw no `second-instance` event. The bridge also needs its own `userData`, because Electron writes `Local State` into it. Pointed at the real profile, it would race the running Chord's `Local State`. |
| Two Chords (`--user-data-dir`, or Chord and Chord Dev) | Each profile folder has its own lock and its own endpoint file, so `chord mcp` finds the one its profile path names: the default by default, `chord mcp --user-data-dir=<path>` for another. In-app profiles are one instance, so there's one endpoint (see the open question below). |

**As built (M1b, 2026-11-20): the window before the DACL is tightened.** Chord tightens the pipe's DACL with `window-owner.exe restrict-pipe` (SYSTEM and the user, the network denied) on the **first connection**, not when it starts listening: running the helper at launch would break the zero-cost rule (Agents on costs one pipe and one file at launch, nothing more). Until that first connection, the pipe has libuv's default DACL, which also gives Everyone and Anonymous *read*. The planning thread accepted this window (review 1 of #76) because:

- read access can open an instance but can't write to it (shown above), so it can never send the token;
- Chord writes nothing on a connection until a valid hello arrives, and hangs up after 2 s;
- the token is the real gate: 32 random bytes, in a 0600 file only the user can read, compared in constant time (`timingSafeEqual`), so a wrong guess says nothing about how close it was.

### 2. `chord mcp` as Chord's own executable

| Question | Seen |
|---|---|
| `ELECTRON_RUN_AS_NODE`? | Not an option: `electron-builder.config.ts` sets the `runAsNode` fuse to false, and should keep it (it's a well-known way to abuse a signed Electron app). |
| stdio in Electron's main | ⚠ On Windows, `process.stdin` is a stub that ends at once, but fd 0 is the client's pipe. `new net.Socket({ fd: 0 })` (or `fs.createReadStream(null, { fd: 0 })`) reads it. `process.stdout` is a `SyncWriteStream` and works. |
| A stray line | ⚠ Electron on Windows writes `\r\n` to stdout before any app code runs (even with `ELECTRON_NO_ATTACH_CONSOLE`). Claude Code 2.1.328, Codex 0.160.1 and the fake client all skip it. Linux doesn't write it. Keep a real-client check per release. |
| ESM main | `await app.whenReady()` at the top level of an ESM entry never resolves: Electron emits `ready` after the entry has evaluated. Use `.then`. |
| Start-up (to the `initialize` reply, Windows, 20 runs) | Electron bridge: **124 ms** median on a quiet machine (115–179), 198 ms while busy. Plain Node, for comparison: 67 ms quiet, 104 ms busy. Linux (WSL, `--ozone-platform=headless`): 123 ms warm. |
| Memory | By default: 3 processes (browser, GPU, network service), 169 MB working set, 54 MB private. With `disable-gpu disable-software-rasterizer in-process-gpu enable-features=NetworkServiceInProcess2 disable-gpu-shader-disk-cache`: **one process, 69 MB working set** (Node: 64 MB). |
| Disk | By default, 1.1 MB of GPU caches per launch. With the switches above, 9 KB (`Local State` and an empty Dawn cache). The branch's `userData` should be a fixed folder of its own, e.g. `<temp>/Chord MCP`. |
| Window, Dock, lock | No window and no `ready` handler. Never the lock (above). macOS should also call `app.dock.hide()` first thing (**macOS CI**, below). |
| Linux with no display (SSH, a headless box) | ⚠ Electron exits before any app code with *Missing X server or $DISPLAY*. `app.commandLine.appendSwitch('ozone-platform', 'headless')` is too late; **`--ozone-platform=headless` on argv works** (123 ms). So the Linux setup line passes it, or a launcher adds it for `mcp` (the Flatpak's `chord.sh` can). |
| The main bundle | The branch must run before Chord's main imports anything. M1 makes `main` a tiny entry that checks argv, then imports either the bridge or `index.js`. |
| Setup lines (Settings shows `app.getPath('exe')`, never a guess) | Windows (per-user NSIS, `oneClick`, `perMachine: false`): `Chord.exe mcp` under `%LOCALAPPDATA%\Programs\` (electron-builder's per-user default; not checked against an installed build), not `Program Files` as the mock drew it. macOS: `/Applications/Chord.app/Contents/MacOS/Chord mcp`. deb/rpm: `chord --ozone-platform=headless mcp`. AppImage: `$APPIMAGE`, which moves when the user moves the file. Flatpak: `flatpak run io.github.anaremore.chord-browser mcp` (its `command` is already `chord`). The Microsoft Store build (off by default) would need an app execution alias. |
| A separate native bridge instead? | It would avoid every ⚠ above and use a few MB, but it's one more signed binary per OS. Not built here. Revisit if the 69 MB per agent session matters: each Claude Code or Codex session starts its own bridge. |

### 3. Identifying the client

| | Claude Code 2.1.328 | Codex 0.160.1 |
|---|---|---|
| `initialize.clientInfo` | `{name: "claude-code", title: "Claude Code", version: "2.1.328", description, websiteUrl}` | `{name: "codex-mcp-client", title: "Codex", version: "0.160.1"}` |
| `protocolVersion` | `2025-11-25` | `2025-06-18` |
| Capabilities | `roots`, `elicitation` (form, url) | `elicitation`, `experimental.codex/auth-change` |
| The bridge's parent chain | `claude.exe` (`%USERPROFILE%\.local\bin\claude.exe`) ← the shell | `codex.exe` (inside the npm package's `vendor\…\bin`) ← `node.exe` (the npm shim) ← the shell |
| The bridge's cwd | The folder `claude` runs in (`CLAUDE_PROJECT_DIR` is also set) | The folder `codex` runs in |
| Environment the bridge gets | Everything the user's shell has | Only an allowlist (`APPDATA`, `LOCALAPPDATA`, `PATH`, `TEMP`, `USERPROFILE`…), so the bridge must find the profile from those alone, which it does |

- **The parent on each OS.** Windows: window-owner.exe gives the name and path from one process snapshot (`pipe-clients` with the client, or `chain <pid> <depth>`), **a few ms** (M1's PowerShell over CIM took ~1 s, and more than 10 s on a busy CI runner: #107); Chord still looks it up while the card shows, never inside a call. Another process's folder isn't available without native code, so the bridge sends its own cwd, which the client chose. Never read `CommandLine`: it can hold tokens. Linux: `/proc/<pid>/exe` and `/proc/<pid>/cwd` (use `exe`'s name, not `comm`: Node's is "MainThread"). macOS: `ps -o ppid=,comm=` and `lsof -d cwd` (**macOS CI**).
- **Spoofability.** All of it comes from the user's own processes: any program the user runs can start `chord mcp` with any `clientInfo`, from any folder, under any file name. It can even skip the bridge and talk to the endpoint with the token. So the card can honestly say only *"Claude Code" wants to use Chord* (in quotes, or "says it's") and *Started by claude.exe in <folder>*. It never shows a verified badge. *Always allow* is keyed on the reported name plus the parent's path, and Settings → Agents says it's a convenience, not a lock. What actually protects the user is that every new connection asks, that the agent works in its own tabs, and that the never-offered list holds.
- **Elicitation** (both clients offer it) is never used for approvals: the agent's own terminal isn't Chord's to trust, and an agent can answer for the user. Approvals live in Chord's window only.

## 5. M1's tools

These are on top of the assistant's tool layer (`ASSISTANT_TOOLS`, its handlers, `pageResult`, `cleanPageText`, the never-readable list), reused, not forked. An agent sees only its own Agent chord's tabs and the tabs shared with it. `tab_id`s are opaque refs (`a1`, `s1`), never Chord's ids.

| Tool | Args | Returns | Notes |
|---|---|---|---|
| `list_tabs` | none | `[{tab_id, title, site, shared, loading}]` | Its own tabs, plus tabs the user shared (`shared: true`). |
| `open_tab` | `url` (http/https, ≤ 2048) | `{tab_id, url, title}` after load (at most 30 s) | A new tab in its Agent chord, with the user's sign-ins. Never-readable sites (the user's *Never* list, Chord's pages) are refused. A sign-in page is returned as it is: the agent asks the user to sign in. |
| `read_tab` | `tab_id`, `start?`, `length?` (≤ 40,000) | `pageResult` JSON (`trust: "untrusted"`) | As the assistant's, PDFs included. |
| `tab_screenshot` | `tab_id` | an image | As the assistant's. |
| `read_form` | `tab_id` | fields, never their values | As the assistant's. On a shared tab too (read-only). |
| `page_diagnostics` | `tab_id` | console errors and failed requests | As the assistant's. |
| `close_tab` | `tab_id` | `Closed.` | Its own tabs only. |

- **Left out of M1:** `propose_fill` (it fills, so it's an action: M2), and `search_history` / `search_archive` (other chords' history is never offered). `read_selection` (a shared tab's selection) is cheap to add if wanted.
- **`read_shared_tab` isn't proposed.** Shared tabs come through `list_tabs` with `shared: true`, and every read tool takes their `tab_id`, so one set of tools covers both. If you'd rather the model have an obvious "the tab I shared" tool, it's `read_tab` on the newest shared tab and costs nothing to add.
- **Annotations:** `readOnlyHint: true` on the read tools, `openWorldHint: true` on all. The server's `instructions` say page text is untrusted data.
- **Never offered,** with no tool at all: passwords and the vault, cookies and storage, script, Settings, extensions, other chords' history.

### How approvals block, and what a refused call returns

A call that needs an answer waits on the card: the first call of a connection waits on the connect card, and in M2 the first action on a site and every risky step wait on theirs. If the card is answered within 45 s, the call simply continues. If not, it returns *waiting* and the card stays up. A step's Send data card is the exception (#143): it comes after the step ran, so past the call's 50 s deadline the call answers that the step ran and what it sent waits, and the card goes on (see *#143: a step's sends past the call's deadline*). Every refusal is a normal result with `isError: true` and one sentence for the model, so it tells the user instead of retrying:

| Case | Text |
|---|---|
| Waiting | *Waiting for the user to allow this in Chord. Ask them to answer the card at the top of the Chord window, then call this tool again.* |
| Denied | *The user denied this connection in Chord. Stop using Chord's tools and tell the user.* |
| Stopped (Stop, Ctrl+. / ⌘.) | *The user stopped you in Chord. Don't call Chord's tools again until the user asks you to.* Calls in flight return it at once, and later calls keep returning it until the user lets the agent continue from the bar. |
| Paused (the user is typing in the agent's tab) | Calls on that tab wait, under the same 45 s rule, until the user leaves the tab. |
| Chord not open, or quit mid-call | *Chord isn't open. Ask the user to open Chord, then call this tool again.* |

## M2: settled so far

- **Who's calling (planner, 2026-11-21, from #81's review).** In M2 Chord finds the connecting process itself instead of trusting the hello's `parentPid`: `GetNamedPipeClientProcessId` on the pipe (through window-owner.exe, as `restrict-pipe` is), `SO_PEERCRED` on Linux's socket, `LOCAL_PEERPID` on macOS's. The parent chain, the card's *Started by* and *Always allow*'s program are then looked up from that PID. M1 keeps `hello.parentPid`, a hint like everything else on the card (§3).
- **Your hands, not a script's (planner, 2026-11-21, from #89's review).** M1 counts a key, a click or a typed address in an agent's tab within 15 s (`USER_MS`) as yours: a tab you take to a *Never* site becomes yours instead of closing. Once M2 acts on pages, check that the input it sends (`sendInputEvent`) never counts as the user's there.

## M2: plan (acting on pages)

*Planning thread, 2026-11-21; approved by the owner 2026-11-22 with the mock `mocks/agents-s18-m2.html` (outside the repo, as M1's was), answers at the end. The owner's decisions above and in the brief (elements, not pixels; the three approvals; Stop and pause; the never-offered list; one shared control layer; peer PID) are settled.*

Outside agents and the assistant gain **click, type and press a key** on a page, plus a few cheap neighbors. They act on elements from an accessibility snapshot, never on pixel positions. Each tool goes through the shared control layer (`main/control/`), so the assistant and outside agents get the same tools, the same gate and the same cards, each in its own place.

### Tools and schemas

All new tools are in core's `CONTROL_TOOLS` with a gate level (`ControlTier`, which already has `act` and `risky`). Every action takes `tab_id` and a `ref` from that tab's latest snapshot. None takes a coordinate, a selector or script.

| Tool | Args | Returns | Level |
|---|---|---|---|
| `snapshot` | `tab_id`, `start?` | The page as an accessibility outline (below), untrusted JSON: `{source: "web_snapshot", tab_id, page_id, snapshot, url, title, range, content}` | `read` (as `read_tab`) |
| `click` | `tab_id`, `ref` | What happened (below) | `act`, or `risky` by what the element is |
| `type` | `tab_id`, `ref`, `text` (≤ 5,000), `replace?` (default true), `submit?` (default false) | What happened | `act`; `risky` with `submit` when the submit is |
| `press_key` | `tab_id`, `key` (one of the list below) | What happened | `act`, or `risky` by the key and what has focus |
| `select_option` | `tab_id`, `ref`, `option` (a choice's label, as the snapshot gave it) | What happened | `act` |
| `hover` | `tab_id`, `ref` | What happened | `act` |
| `navigate` | `tab_id`, `url` (http/https, ≤ 2,048) | `{tab_id, page_id, url, title}` after load (at most 30 s, as `open_tab`) | none (as `open_tab`): its own tabs only |
| `back` | `tab_id` | The same | none: its own tabs only |

- **`snapshot` is a new tool, not an extended `read_tab`.** `read_tab` stays the cheap way to read an article. A snapshot is a different shape (an outline with refs), and a model that only reads shouldn't pay for refs. `read_tab`'s description points to `snapshot` for acting.
- **`select_option` and `hover` are nearly free.** `select_option` reuses the fill's select writer (`forms.ts`: set the index from the isolated world, then `input` and `change`), because a native `<select>`'s popup is a separate widget that trusted input can't drive reliably. `hover` is `click`'s path without the button. Both are in.
- **`navigate` and `back` are cheap** (`loadURL` and `navigationHistory.goBack()`). They follow `open_tab`'s rules: the *Never* list, http(s) only, and the agent's own tabs. They need no site card, since going to an address is what `open_tab` already does. `forward` is left out (no one asked; trivial to add).
- **What an action returns:** `{ok: true, page_id, navigated, url, title, notes?}`. `navigated` says the page id changed, so the agent knows its refs are stale; `notes` carries what M1 already holds for the next result (a dialog, a popup, a download). It waits for the page to settle: a navigation's load (at most 10 s, then `loading: true`), otherwise up to 500 ms for the page to stop changing (a `MutationObserver` in the isolated world, quiet for 100 ms). Each result ends with *Call snapshot again before using refs from before.* when `navigated` is true. Actions don't return a fresh snapshot (it costs up to 40,000 characters a turn); the agent calls `snapshot` when it needs one.
- **The assistant** gets the same eight tools (below, *The assistant's side*). Annotations: `readOnlyHint: false` and `destructiveHint: true` on `click`, `type` and `press_key`; `destructiveHint: false` on `hover`, `select_option`, `navigate` and `back`.

**`press_key`'s keys:** `Enter`, `Tab`, `Shift+Tab`, `Escape`, `Backspace`, `Delete`, `Space`, `ArrowUp`, `ArrowDown`, `ArrowLeft`, `ArrowRight`, `Home`, `End`, `PageUp`, `PageDown`. Nothing else: no letters (they'd be a web app's shortcuts: Gmail's `#` deletes), no Ctrl, Alt, ⌘ or function keys, so an agent can never press one of Chord's or the OS's shortcuts (Ctrl+W, Ctrl+L, Ctrl+., F12). Text goes through `type`.

### The snapshot and its refs

**What it is.** The main frame's accessibility outline, in the indented text form Playwright MCP made familiar:

```
- banner
  - link "Home" [ref=e1]
  - searchbox "Search orders" [ref=e2]
- main
  - heading "Your orders" [level=1]
  - list
    - listitem
      - link "Order #1043 · Nov 12" [ref=e3]
      - button "Start a return" [ref=e4]
  - checkbox "Gift receipt" [ref=e5] [checked]
  - textbox "Password" [password: sign in yourself]
```

- **Built in the isolated world (4400)**, as forms and the extractor are, by one plain-JavaScript script: roles from the element (`role`, else the implicit role of the tag and type), names from `aria-labelledby`, `aria-label`, labels, `alt`, `title`, then text, as the read script already does. Open shadow roots are walked; frames are listed by title, not entered (as forms; same-site frames are a later slice).
- **Not the debugger's accessibility tree** (`Accessibility.getFullAXTree`). It's Chromium's real tree, but it needs the debugger attached (one client at a time with screenshots and diagnostics, `debugger-queue.ts`), it's slow on big pages (hundreds of milliseconds and megabytes of JSON), and its node ids can't be held against a page that changes. The isolated world keeps each ref's element by a `WeakRef`, out of the page's reach, exactly as the fill keeps fields.
- **Only what can be acted on gets a ref:** links, buttons, text fields, text areas, contenteditable, checkboxes, radios, selects, switches, tabs, menu items, options, `summary`, and any element whose computed `cursor` is `pointer` and has no ref'd ancestor (sites' clickable `div`s). Headings, lists, landmarks and plain text are there for orientation, without refs. Hidden elements are left out by forms' `shown()` rule.
- **States, never values.** Each ref says `[checked]`, `[selected]`, `[expanded]`, `[pressed]`, `[disabled]`, `[required]`, and a select's current choice by label. Text fields never show what's in them (forms' rule: the page can hold your data), only `[empty]` or `[filled]`. A password or one-time-code field (forms' `classifyField`, *sensitive*) has no ref and says *sign in yourself*.
- **Bounded:** at most 20,000 elements looked at and 150 ms of looking, at most 2,000 refs, names cut to 120 characters, the outline in ranges of 40,000 characters (`start`, as `read_tab`). Past a bound, a note says what was left out.

**Refs.**
- **Format:** `e<n>`, counted per tab and never reused in that tab (as form fields' `f<n>`), so an old ref is never taken for another element. The call names the tab too: `{tab_id: "a1", ref: "e14"}`.
- **Lifetime:** a ref is good only from the tab's **latest snapshot**, on the same page (`page_id`). A new snapshot, a main-frame navigation (the page id changes), or the tab closing makes every older ref stale.
- **At each action** the ref is checked again, from the element as it is now: still connected, still shown, still the same role and name as the snapshot said. Any no, and nothing is sent.
- **Refusals,** one sentence each, `isError`:

| Case | Text |
|---|---|
| A ref never made in this tab | *There's no element e99 in that tab. Call snapshot for the page's elements.* |
| From an older snapshot, or the page moved on | *That ref is from an earlier snapshot. Call snapshot again, then use its refs.* |
| The element changed or went | *That element changed since the snapshot (it's gone, hidden, or now says something else). Call snapshot again.* |
| Covered (the hit test) | *Something is covering that element: dialog "Cookie settings" (e31). Deal with it first, or call snapshot again.* |
| Disabled | *That element is disabled.* |
| `type` into what isn't editable | *That element doesn't take text.* |

### How an action is sent

**Trusted input through `webContents.sendInputEvent`, at the element's center after scrolling it into view and a hit test.** In detail:

1. **Resolve** the ref in the isolated world and check it (above).
2. **Scroll it into view** (`scrollIntoView({block: 'center', inline: 'center', behavior: 'instant'})`) and read its box, clipped to the viewport.
3. **Hit-test** at the box's center: `elementFromPoint` (through open shadow roots) must be the element or inside it. If not, try the centers of the box's other visible quarters, then refuse as *covered*, naming the cover's role and name (and its ref, if it has one).
4. **Send:** the point in the view's coordinates (CSS px × the zoom factor, `webContents.getZoomFactor()`); `mouseMove`, `mouseDown`, `mouseUp` with `clickCount: 1`. `type` clicks to focus, selects what's there when `replace`, then `webContents.insertText(text)`, which arrives as one trusted text insertion (`beforeinput` and `input` fire), handles any language without an IME, and is no keystroke, so no page shortcut fires. `press_key` sends `keyDown` (with `char` where the key has one) and `keyUp`.
5. **Show it** (below), then wait for the page to settle.

**Why not the alternatives:**
- **Events dispatched from the isolated world** (`el.click()`, synthetic `KeyboardEvent`s) are `isTrusted: false`. Many sites ignore them (and they should), and they skip the browser's own behavior (focus, default actions, user activation for popups and clipboard).
- **The debugger's `Input.dispatchMouseEvent`** is trusted too, but holds the debugger (one client at a time) for every action. It's the **fallback** if the spike (M2a) finds that `sendInputEvent` doesn't reach a parked, hidden agent tab on some OS. Never exposed to the agent either way: raw CDP stays never offered.

**Your hands, not a script's (from #89's review).** `sendInputEvent` goes through the same path as your keys and clicks, so Chord's `before-input-event` and `before-mouse-event` see it. Three listeners must tell them apart: the pause (a key in an agent's tab pauses it), `USER_MS` (an agent tab you take to a *Never* site becomes yours), and shortcuts (`keyboard.ts`). Main marks each event it sends: a per-WebContents queue of what it's about to send (type, key or button), taken off as each handler sees it. An event at the head of the queue is the agent's; anything else is yours. The spike checks whether the handlers run synchronously inside `sendInputEvent` (then a simple *sending now* flag is enough) on Windows and Linux. *Unit test:* the three handlers with a fake WebContents, for both kinds of input.

### What counts as risky

Every action is classified **before it's sent**, in core (`control-risk.ts`, a pure function over a description the isolated world gives: the element's role, tag, type, name, its form's method, its form's fields' kinds). One of: `act` (asks once per site), `risky` (asks every time) with a **why** (*submit*, *pay*, *send*, *delete*, *sign out*, *sign up*), or `refused`. Generous on purpose: a step that asks needlessly costs a click; one that doesn't ask costs much more. Words are matched as whole words, case-insensitively, in US English first (other languages fall back on the structure: form submits and payment fields need no words).

| The action | Class | Why |
|---|---|---|
| Click a link (`a[href]`) whose name has no risky word | act | Following a link is reading. |
| Click a link or button named *Pay*, *Buy*, *Purchase*, *Place order*, *Checkout*, *Complete order*, *Donate*, *Subscribe*, *Upgrade*, *Book*, *Reserve*, *Confirm purchase* | risky · pay | |
| … named *Send*, *Post*, *Publish*, *Reply*, *Comment*, *Share*, *Invite*, *Tweet*, *Submit* | risky · send / submit | |
| … named *Delete*, *Remove*, *Trash*, *Discard*, *Erase*, *Cancel subscription*, *Close account*, *Unsubscribe*, *Revoke* | risky · delete | |
| … named *Sign out*, *Log out* | risky · sign out | The agent's tabs share your sign-ins: signing out there signs you out. |
| … named *Sign up*, *Create account*, *Register*, *Accept*, *Agree* | risky · sign up | It makes an account or a promise in your name. |
| Click a submit button (`button` in a form with no `type`, `type=submit`, `input[type=submit|image]`) | risky · submit, or the stronger why its form or name gives | |
| … where the form is a **search**: method GET and inside `role=search`, or with a `type=search` field, or with one text field and no others | act | Searching is reading. |
| … where the form has a payment field (`autocomplete` `cc-*`, `transaction-amount`, or forms' payment words) | risky · pay | |
| … where the form has a password field | risky · sign in | Agents never type passwords, so you typed it. |
| `type` with `submit: true` | As clicking the form's submit button (above); a field in no form: risky · send | Enter after text is how chat boxes send. |
| `press_key Enter` in a form's text field | As its form's submit (above) | Enter submits a form. |
| `press_key Enter` in a text area or contenteditable | risky · send | Chat apps send on Enter. Newlines go in `type`'s text instead. |
| `press_key Enter` or `Space` on a button or link | As clicking it | |
| `press_key Delete` or `Backspace` outside an editable field | risky · delete | Web apps delete on these keys. |
| Other keys, and `Delete`/`Backspace` in a text field | act | |
| `type` into a text field, `select_option`, `hover`, checking a checkbox or radio | act | Nothing leaves the page until a submit. |
| `type` into a password, one-time-code or payment-card field (forms' *sensitive*) | refused | *Chord never lets agents type passwords, codes or card numbers. Ask the user to fill it.* |
| Click a file field (`input[type=file]`) | refused | *Agents can't pick files.* |
| An element inside a frame | refused (no ref) | Frames aren't entered in M2. |
| Anything on a *Never* site, a Chord page, or a private window | refused | As reading. |

### The cards

Both are the gate's cards (`site` and `step`, which `control-gate.ts` already has). For outside agents they show where the connect card does: the window used last, in its popover, centered at the top, never taking the keyboard, with `promptInputDelay`. For the assistant they're inline in the chat (below). Text from the page (an element's name) is quoted, cut to 60 characters, and goes through `plain()`. **The agent's own words never appear on a card**: the card says what Chord sees the agent doing, not what the agent says it's doing, since a page can steer the agent's words.

**The site card** (the first action on each site, by its registrable domain with the Public Suffix List and private suffixes on, `loginSite`, as sharing does):
- ✳ *Let Claude Code click and type on shop.example?*
- *It wants to click “Start a return”.* (the first action, in Chord's words: *click “…”*, *type in “…”*, *press Enter in “…”*, *choose an option in “…”*, *point at “…”*)
- *It still asks before it submits, pays, sends or deletes anything.*
- **Deny** (quiet word) · **Allow for now** (outlined pill) · **Always on this site** (filled accent pill). × is Deny.
- **Allow for now** lasts while the agent stays connected (the assistant: this chat).
- **Always on this site** keeps the site with the agent's allowance (`AgentAllowance.actSites`, at most 100, least recently used dropped). It's offered only to an agent you always allow; one you let in once sees **Allow for now** alone. Settings → Agents lists the sites under the agent, each with Remove.
- **Deny** refuses this action and the agent's other actions on the site until it reconnects, so a page can't make it ask again and again. The agent hears *The user didn't let you act on shop.example. Don't act there again unless the user asks you to.*

**The risky-step card** (every time, never remembered: `grantAfter('step', …)` already returns null):
- ✳ *Place the order on shop.example?* The title is the why: *Submit this form*, *Place the order* (pay), *Send this* (send), *Delete this* (delete), *Sign out* (sign out), *Create an account* (sign up), *Sign in* (a form with a password).
- *Claude Code is about to click “Place order”.*
- For a form: what goes with it, by field label, for up to 6 fields (*Name, Email, Address and 2 more*), never values. The values are in the page: **Show me**.
- **Show me** (quiet word): shows the agent's tab in this window and outlines the element, card still up. · **Don't** (outlined pill) · **Allow** (filled pill; with `danger`'s color for *delete* and *pay*). × is Don't.
- The agent hears *The user said no to this step. Don't try it another way; ask the user what to do.* on Don't.

**What *waiting* means for each.** Unchanged from M1: a call waits on its card for 45 s (`CONTROL_WAIT_MS`), then returns *waiting* and the card stays up. A **site** answered late counts for the agent's next action on that site. A **step** answered *Allow* late counts only for the same step: the same tab, page id, ref and action, within 2 minutes (the gate's `late` table already works this way, by address). The action is never run by the answer alone; the agent calls it again, and the classification runs again on the page as it is then. A **Send data** card is different (#143): the step already ran, so it's never re-run; past the call's deadline its card is handed over, and its answer sends or drops what the page sent, the outcome told with the next result.

### While it acts: the bar and the element

- **The bar** (M1's, blue) says what it's doing, in present tense, with Stop: *Claude Code is clicking “Start a return”* · *typing in “Search orders”* · *pressing Enter* · *choosing “Express” in “Shipping”* · *going to shop.example/returns* · *going back*. Between actions it falls back to *Claude Code is working in this tab*; with a card up, *Claude Code is waiting for you*; reads keep *is reading this tab*. - **Your hands first:** a key or a click of yours in the tab pauses it there (M1); the agent's own input never does (above).
- **Stop** and Ctrl+. / ⌘. stop it as in M1. An action already sent can't be taken back; one not yet sent isn't sent.

### WebMCP (later)

*Owner, 2026-11-21: make M2 WebMCP-ready, and pass sites' own tools (`document.modelContext`) through in a later milestone. What's reported about WebMCP (an Origin Trial in Chrome 149–162; the API moved from `navigator` to `document` and lost `provideContext`; an experimental CDP `WebMCP` domain with `toolsAdded` and `invokeTool`) is from a review, not checked here; that milestone checks it against Electron's Chromium first.*

- **Not in M2.** Passing site tools through waits until Chromium ships `document.modelContext` on by default and the spec settles. M2 enables no WebMCP feature flag.
- **Fixed tool names.** M2's tools are short and fixed. Site tools will come later behind fixed meta-tools (`list_page_tools`, `call_page_tool`), never by changing `tools/list` as pages come and go: clients cache it (Antigravity reportedly caches schemas on disk).
- **One page boundary.** `ControlPage` stays the only thing that touches a page, whether through the isolated world or the debugger (`debugger-queue.ts`), so the CDP `WebMCP.*` domain can plug in behind it later with neither front door changing.
- **Cards and grants that fit.** The site and step cards carry a structured target and arguments (`ControlCard.target`, plus `args` from M2c: the element's role and name, or later a tool's name and its arguments), not prose alone. M2's site grants are per registrable domain, as settled; site tools' grants will be per origin, a finer key the same gate can hold (`grantKey`'s subject).
- **Pages never lower the bar.** A page's own hints (a tool's `readOnlyHint`, ARIA, form attributes) never turn a risky step into an action that doesn't ask; they can only make one ask. Chord never injects a WebMCP shim into a page's main world.
- **Untrusted, and only where reading is allowed.** Site tools' names, descriptions, schemas and outputs are untrusted data, wrapped like page text (§11.4). Only the main frame's own, same-origin tools are offered, never in a private window, on a Chord page or on a *Never* site. The assistant gets them through the same gate.

## M2e: threat checklist (before the design)

*Planning thread, 2026-11-23, revised 2026-11-24 after Neon's design review (below, *Neon's design review*). The process is the owner's (2026-11-24): every way acting from the assistant could go wrong, and M2e's answer to each, before any design. This reads M2d (#112) as of its round 4 and its extensions note.*

**What's different about your tabs.** Everything M2c and M2d built hardens an *agent's* tab, a tab Chord made for the agent: its page is untrusted, and the agent is let in by a card. M2e acts in **your** tab, the one on screen. Three things change:

1. **The page already has your sign-ins.** It runs in your chord (Personal, Work…), your vault fills it, your extensions run in it, and it can send what it likes to its own site without any agent. What the assistant adds is what the page *can't* do alone: **trusted input** (a real click, with the user activation that opens popups, pickers, passkey prompts, the clipboard), **reach to other sites** (a click or an address that leaves the page), **data from outside the page** (other tabs, history, the archive, earlier turns of the chat), and **your intent, borrowed** (a step you never asked for).
   That stance has two holes, and the plan treats both as real (Neon's S1): a page that *is* hostile can't send another tab's data until the assistant types it in (B3, C4–C6 then matter), and an honest app full of other people's content (mail, a code host, a chat, a card table's chat) never sends a change without trusted input, so a click an injected instruction talked the assistant into is exactly what C4–C6 can't see.
2. **The tab has state you care about.** A half-written email, a form you filled, a hand of cards.
3. **You're right there.** Typing in the page or the chat, switching tabs, closing the one it's working in.

### What could go wrong, and M2e's answer

Each item says where its answer comes from: **carries over** (M2c or M2d, unchanged), **new in M2e**, or **stated limit** (not closed, and said so).

**A. Acting on your signed-in tab**

- **A1. It acts in a tab you didn't mean.** It acts only in *the message's tab*: the tab on screen, in the window the message came from, when the message was sent (for a queued message, a retry, or *Make with Codex*: when you sent it, kept with it), and only while that tab is still on screen there (shown alone, not in a split; the window not minimized). Once it's off screen for any reason (you switch tabs, a popup takes the screen, the tab moves windows, you switch chats), acting ends **for the rest of that message**, even if it comes back: *The user switched away from that tab. Stop, and tell them what's left.* Never a private window, a chord where the assistant is off, a *Never* site, a Chord page, Peek, a mini window, an agent's tab, or with *Nothing* or *Click and type on pages* off. A split is refused in M2e (*Acting works on a tab shown alone.*): the agent bar and its Stop show only over a tab alone (`syncAgentBars`), and `activeTab` names one pane. *New in M2e.*
- **A2. It acts on a site you didn't mean.** The first action on each site in a chat asks (the inline site card), per registrable domain. *Always on this site* is kept in `settings.assistant.actSites`. *Carries over* (the gate's `site` card, inline).
- **A3. It wipes what you wrote.** `type` replaces a field's text by default. The activity row says *Replaced the text in “Subject”* when the field wasn't empty. In a plain text field or text area the text goes in by `insertText`, so the field's own undo (Ctrl+Z / ⌘Z) brings yours back; date, time, month and week fields, `select_option` and many rich editors set values in ways undo doesn't reach (Neon's S3). The instructions say to add to a field you filled unless you asked to replace it. *New in M2e.* The `values` check (M2d's bug 1) *carries over*.
- **A4. Your passwords vault** (Neon's B2, confirmed). A username field isn't sensitive, so the assistant can focus it; focusing it opens the vault's menu (`PasswordAssist.focused`, assist.ts), and while that menu is open `guardKeys` takes the page's Enter and arrows **with no `isAgentInput` check**, so the assistant's `press_key Enter` would fill your saved password. Requirement: `PasswordAssist` ignores agent input (its key guard and its focus handler check `isAgentInput`), and while the assistant's action or its after-window (B3's) is on a tab, the menu stays closed there and any open one closes. A password, code or card field has no ref and `type` refuses it (*carries over*). *New in M2e*, with E2E rows both ways.
- **A5. Your extensions.** They run in your tab as always. What they put in the page is in a closed shadow root (refused: M2d review 1) or a `chrome-extension://` frame (no refs). *Carries over.*
- **A6. Trusted input opens things a script can't.** The assistant's click gives the page user activation for 5 s in the renderer. Main's **after-window** is 6 s from the action's last input (Neon's S3: the margin covers the lag between the renderer and main), and ends at once on your own input (B3's lease). During the action and its after-window, in that tab:
  - *File pickers* intercepted (`Page.setInterceptFileChooserDialog`) and never shown; the result says so. *Carries over*, for the window.
  - *Passkeys and security keys* (Neon's B1, confirmed: `passkeys.ts` only answers `select-webauthn-account`, which `create()` never raises and Windows never raises at all). Requirement: WebAuthn `get` and `create` from the tab are answered before any system prompt. **Spike first** (M2e-2's first commit): CDP `WebAuthn.enable({enableUI: false})` with no virtual authenticator, on the page and its frames for the window, so the page's call fails as *not allowed*, on Windows (the system's own dialog), macOS and Linux. If the spike can't stop the system's prompt on a platform, the fallback is honest: the prompt can still appear, it needs your touch or PIN to do anything, and the chat says *The page asked for a passkey after the assistant's click. Cancel it unless you meant to sign in.* `passkeys.ts` declines its own chooser during the window too (defense in depth). *New in M2e.*
  - *PaymentRequest and FedCM* (Neon's B1): M2d's agent tabs refuse them by header (`AGENT_POLICY`); your loaded page can't be given a header. The spike checks whether Electron 45 implements either at all (a browser must supply their UI; Chord supplies none). Unimplemented: nothing to do, a test row keeps it so. Implemented: refused during the window (CDP `FedCm.enable` and dismiss; PaymentRequest by the session's handler, if Electron has one, else a stated limit). *Pushback on Neon:* M2e doesn't assume these work in Electron until checked.
  - *Popups* (Neon's B5, confirmed: `openFrom` lets `window.open` with features make a real window with `window.opener`, unwatched, in front). During the window: **nothing it opens is opened**: a window (an OAuth or payment popup the assistant set off is yours to open), a new tab in front or behind, another scheme. The chat says *The page tried to open … in a new tab or window; it wasn't opened*. *As built (Neon's B1 on #150):* a new tab was first planned to open in the background, but it would load with no lease of its own (a download saved unasked, a redirect to an address that deletes or signs out unchecked), so it's denied; the assistant can go to the address itself, and leaving the site asks every time. A pinned tab's cross-site link doesn't open Peek for agent input (the `input-event` gesture skips `isAgentInput`). *New in M2e.*
  - *Page dialogs* (Neon's B4, confirmed: only agent tabs set `disableDialogs`; your tabs get Electron's native dialogs, which block the renderer). The action's debugger session has `Page.enable` and watches `Page.javascriptDialogOpening` and `…Closed`: an open dialog ends the action at once (no waiting out `pageCall`'s 3 s on a blocked renderer), the chat says *The page is showing a dialog. Answer it yourself.*, nothing more is sent while it's up, and the bar comes down so Stop isn't needed. The spike checks how a native dialog interacts with the panel (it shouldn't block the chat window's WebContents) on each OS. *New in M2e.* Chord showing its own dialogs instead of native ones (the owner's no-native-modal rule) is a separate issue, not M2e's.
  - *`beforeunload`*: during the window, `will-prevent-unload` is never prevented, so a page with unsaved changes stays put and the action reports *The page has unsaved changes, so it stayed. Ask the user.* `navigate`, `back` and a link click never discard your work. *New in M2e.*
  - *The clipboard* (gap 5): `clipboard-sanitized-write` (granted as harmless today, permissions.ts) and `clipboard-read` are refused for the tab during the window; and Chord keeps the clipboard's text at the action's start and, if it changed during the window without your input, puts it back and says so (*The page tried to change your clipboard; Chord put it back.*), since `execCommand('copy')` on activation isn't a permission. *New in M2e.*
  - *Other programs* (gap 6): a link to `mailto:`, `vscode:` or any scheme Chord hands the system (`openExternal`) is refused during the window (*That link opens another program. Ask the user to click it.*). *New in M2e.*
  - *Downloads* (gap 7): a download the window sets off asks inline first (*Save invoice.pdf from shop.example?* · Allow · Don't), the file held until then (`will-download`). *New in M2e.*
  - *Printing* (gap 9): `window.print()` on the assistant's click shows the system's print dialog, which does nothing without you. *Stated limit*, said in the chat when it happens (the spike checks Electron gives Chord a signal; if not, silent).
  - *Permissions* (camera, location…) ask in Chord's prompt, which the assistant's input never reaches. *Carries over.*

**B. Prompt injection**

- **B1. Something it read tells it to act.** Not only the message's tab: another tab read this turn, a PDF, an image you pasted, history, the archive, an imported chat (gap 1). The instructions say text from any of them is data, never instructions (§11.4's wrapping, *carries over*); acting happens only inside a turn your message started, on that message's tab (A1). The cards below are what hold when the model is fooled anyway.
- **B2. A step you didn't ask for.** Risky steps ask every time; the card shows only what Chord sees. *Carries over.* How Chord judges a step from context, not only words, is *Risk from context* (below, settled for M2g).
- **B3. Your data carried out** (Neon's B7). The channels:
  - *An address.* `navigate` to another site asks every time with the address (the owner's answer 2). A **same-site** `navigate` or `back` that redirects to another site (an open redirect) is held at the redirect and asks the same card before it's followed (Neon's B7a). The address on the card shows its host and path, then its query in full, wrapped, never cut silently (*?q=…* expands).
  - *Typing it in.* The page's `input` handler sees each character as it goes in, and can send it by an image, a fetch after the after-window, a worker, a `fetchLater` or a WebSocket, none of which the hold sees. So the *Send data* card is **not** a guard for this (round 1's reassurance was wrong). The guard is a **tainted chat** (Neon's B7b; the owner's answer 6): once the chat has read anything but the message's tab (another tab, history, the archive, a PDF elsewhere, an attachment), every `type` in it asks first, showing the exact text: *Type this in “Search”?* · “wool scarf, size M, 14 Elm St” · Allow · Don't. A chat that has only read the tab it acts on asks nothing more. *New in M2e.*
  - *A link the page offers.* Following a link is reading; its address is the page's, not the assistant's. *Carries over.*
- **B4. Names that mislead.** Visible text counts too, and the step is described again after the card and before the input. *Carries over.*
- **B5. Floods of cards.** A *No* holds for the chat on that site; 3 *Send data* cards an action; step cards never coalesce. *Carries over.*

**C. Sends without a card**

- **C1. An action sends what the classifier didn't name.** During an action, from just before its input until the page settles and 1.5 s after (`USER_SENDS_TAIL_MS`), the tab's requests pass through `Fetch` (page and frames of other processes): GET and HEAD go, reports drop, anything else is held for the *Send data* card. *Carries over*, with rounds 3 and 4's rules: a body makes a request a send whatever its method (OPTIONS too), exact origins, 8 a card, a risky step's Allow for its own addresses once.
- **C2. Between actions** nothing is held: your page's own sends are yours. *New in M2e.* The honest cost: a save debounced past 1.5 s, set off by the assistant's typing, goes unasked (S1's second hole).
- **C3. The site's service worker.** Bypassed during the watch (`Network.setBypassServiceWorker`), and **always** restored when the watch ends, whatever ended it (Stop, a timeout, an error, your input, the tab closing; Neon's S3). The result notes the bypass. *Measured before it's settled:* fixture apps whose worker answers an API route or adds an auth header, with the bypass on.
- **C4. Workers the page already runs, shared workers, cross-tab channels** (`BroadcastChannel`, storage events, the Reporting API; gap 10). *Stated limit* (the owner's answer 4).
- **C5. `fetchLater` and keepalive sends after the window.** *Stated limit.*
- **C6. Live connections** (WebSocket, WebRTC, WebTransport). *Stated limit, carries over.* A card table over a WebSocket is guarded by the site card and the classifier alone.

**D. Risky steps**

- **D1.** The classifier, the step card, *Show me*, the re-description, *Don't*: *carry over*, inline.
- **D2. Waiting.** The assistant's cards wait as long as it takes, except what holds your page's requests (*Send data*, a download): 45 s, then dropped (*Not answered in time, so nothing was sent*). *New in M2e.*
- **D3. Game moves aren't payments** (the owner, 2026-11-24). *Fold*, *Call*, *Raise*, *Bet*, *Wager* and *All in* are ordinary clicks. A real payment asks through the pay words and payment-card fields. No new words. *Carries over.*

**E. Teardown, crash, navigation, frames**

- **E1. You close the tab mid-action.** The action ends (*That tab is closed.*), its cards come down, what's held fails, the watch's lease is let go of. *New in M2e.*
- **E2. You reload, go back or forward, or type an address.** You taking over (F1). *New in M2e.*
- **E3. The renderer crashes.** The action ends; nothing reloads it. *Carries over.*
- **E4. The page navigates during an action.** The page id check, a document to a delete or sign-out address asking, refs going stale. *Carries over.* `beforeunload`: A6.
- **E5. Frames.** No refs in frames (M2g's); a hit on a frame isn't the element's. Text or keys whose focus moves into a frame between the check and the input **land there before anything can stop them**: your tabs' frames have no guard (Neon's S3, gap 11). Chord detects it after (the guard never sees the last event) and the action fails, but what was typed reached the frame. *Stated limit.*
- **E6. The chat ends, or its rules change, mid-action.** You close the panel, start or switch chats, change the model, turn *Click and type on pages* off, set *Nothing*; the provider exits; the window closes; Chord quits. Acting stops at once, held sends fail, acting cards come down, as `readsNothing` already stops reads (Neon's S2). *New in M2e.*
- **E7. DevTools open on your tab**: nothing pressed or typed. *Carries over.*
- **E8. Two chats on one tab**: one watch a tab; the other is refused. *Carries over.*

**F. Focus, keyboard, and you**

- **F1. You use the tab while it acts.** Your key or click in the tab, your reload, back, forward or typed address: acting ends **for this message**; the action in flight sends nothing more, held sends fail, cards come down, the chat says *Stopped: you used the tab*. Your next message acts again (the owner's answer 5). *New in M2e.*
- **F2. You use the tab right after it acted** (Neon's B3). Your own input ends the after-window and the tail **at once**: your click, picker, passkey, download or clipboard right after the assistant's is never caught. What was already held for the assistant fails; nothing of yours is held. No chat row after a finished turn. *New in M2e.*
- **F3. You type in the chat while it acts.** The assistant's input goes to the page's WebContents only. *Carries over*, with an E2E row.
- **F4. Keys or text in the wrong place.** The typing guard, dormant in Chord's page preload (top frame), armed only during an action. Frames: E5. *New in M2e.*
- **F5. A key does something of Chord's.** The key list, `agentInputAllowed`, `keyboard.ts`. *Carries over.*
- **F6. A card answered by mistake.** Acting cards take no key and **no click** in their first 500 ms (`promptInputDelay`, as the vault's menu and the generator row, Neon's S3), and take keys only once focused. The composer's ⌘↵ / Esc (Assistant.tsx' `onKey`, which answers a pending read card) skips acting cards. *New in M2e.*

**G. An outside agent's tabs**

- **G1. Read without being asked.** Agent chords' tabs are left out of `list_tabs` and every read unless the message points at one: it was on screen when you sent it (the window's `agentTab`, which `activeTab` must read first: Neon's S2), or you attach it (attachable tabs gain agents' tabs, named *Claude Code · Title*). Pointing is per message: the next message points again or the tab is out of reach (a queued message keeps what was attached when you sent it). *Mentioned* is deferred: the composer has no way to mention a tab yet. *New in M2e.*
- **G2. Acting in one.** Never: *That tab is Claude Code's. Keep it first to make it yours, then I can act in it.* *New in M2e.*
- **G3. Its reads disturb the agent.** The assistant's snapshot is its own owner's. *Carries over.*
- **G4. You close or reload an agent's tab** (M2d's record, *Your hand on an agent's tab*). Close: its action ends and its cards drop (*carries over*). Taking over comes **only from your own entry points** (Neon's B6, confirmed: a pause makes the send hold's `whose()` `'user'`, so a page's own `location.reload()`, meta refresh or timed redirect, if it counted, would turn the hold off): the toolbar's reload, back and forward (browser.ts), the context menu (context-menu.ts), the app menu and keys (index.ts' page actions), the sidebar's reload (`reloadTab`), the address bar, and settings that reload tabs (the ad-blocking toggle). Each calls `AgentChords.takeOver` (as built: reload, back, forward and an address through `takeOverPage`/`browser.userNavigates`; the reader view's link, Safe Browsing's *Back to safety* and *Visit anyway*, and a search by image into the tab too): what the page held fails, the tab's cards are let go of (its asks answer no; a site card another tab waits on stays up for that tab alone), and, **only if a window shows the tab**, the agent is paused there (a tab no window shows stays the agent's and held: #116's review). The agent hears the paused refusal (*The user is using this tab right now*), not a per-reason wording; a card's no that was a takeover, a close or Stop says so (*The user took that tab over…*), never *the user didn't let you*. Refs go stale by the page id as for any navigation. Moving the page yourself, everything of the outgoing page's that reaches the send hold (its `pagehide` keepalive POST, a beacon, a form it posts, an address that signs out) is no one's and fails, until a new document has committed in the main frame and stopped loading; only the address you asked for goes (once, as the page's own document). It fails closed (Neon's round 2 on #116): a pushState, a hash or `window.stop()` of the outgoing page clears nothing, and a move that fails or doesn't commit within 15 s gives the tab back to the agent (unpaused, held), never to you. A tab no window shows keeps its typing guard up for the action, which hears of the takeover. Closing an agent's tab (×, middle-click, Ctrl+W, its menu, Close all, a *Never* site) lets go of its cards at once, unpauses it, and clears its bar. Never `did-start-navigation`. Keys in the page (F5, Ctrl+R) already pause it (*carries over*: `yours()`). *New in M2e.* *Correction:* round 1 named `nav.ts`, which only trims saved history.

## M2e: plan (the assistant acts in your tab)

*Planning thread, 2026-11-23, revised 2026-11-24; the mock is `mocks/agents-s18-m2.html` §7 (outside the repo). The owner's decisions (2026-11-23): the assistant acts on the tab on screen (one of their examples: a card game's Fold, Call and Raise); the same control layer as outside agents; it reads agent tabs only when you ask and never acts in them; you can close or reload agent tabs. Each rule names its checklist item.*

### What people will use it for

*The owner, 2026-11-24: the card game is one example among many, not the design's center.* Every case acts only in the message's tab (A1), asks the site card on its first action on a site (A2), and ends when you use or leave the tab (F1). What each adds:

### Tools

The eight tools of `ACTION_TOOLS`, same schemas, through `duetScope`'s new `act` host. Every action names the tab; anything but the message's tab, on screen, is refused (A1). `propose_fill` stays as it is.

- **The message's tab** (`DuetChat.actTab`: the node and window): set when a message is sent, from the tab on screen then; a queued message keeps its own (the queue holds `{text, actTab}`, not a string); `retry` and *Make with Codex* reuse the original message's. Cleared when the turn ends, and for good for that message once it's off screen (A1).
- **`mayAct(node)`**: null only for the message's tab, on screen alone in its window, readable, not an agent's, with acting on.
- **`navigate`**: same site, the site card; another site, the leaving card every time; and its load is held at a redirect to another site for that card (B3). **`back`**: the entry it goes to, by the same rule.
- **Results** add notes for what A6 caught: a popup or new tab denied, another program refused, a download asked, a dialog, the clipboard put back, the service worker bypassed.

### The watch (your tab), a lease

`control/sends.ts`' hold is today an agent tab's for life (`holds`, one `action` at a time, `watchSends` refusing a second). Your tab gets a **lease** instead (`control/user-watch.ts`), so the debugger queue is never held for a window (Neon's B3, confirmed: `openDeep` itself runs inside `withDebugger`, a FIFO queue, so holding it for the window would deadlock the action's own checks and stall the next action, `page_diagnostics` and screenshots):

1. **Acquire** (inside one short `withDebugger` turn): attach if no one is, auto-attach frames (held at their start), `Fetch.enable`, `Network.setBypassServiceWorker(true)`, `Page.enable` with dialogs watched, `Page.setInterceptFileChooserDialog`, `WebAuthn.enable` (per the spike), and register the tab with `passkeys.ts`, `PasswordAssist`, permissions.ts, the window-open handler, `will-download` and `will-prevent-unload`. A second lease on the same tab (the next action) **joins** it: it ends the first action's tail at once (asking any card that tail holds as the second action's), and restarts the after-window from its own last input. `openDeep` uses the attachment as it does an agent tab's (`mine` false).
2. **Hold**: the action's input, settle, and the 1.5 s send tail; the 6 s after-window for activation. Only timers: no queue held.
3. **Release** (one short `withDebugger` turn), when the after-window ends, your input comes (F2), Stop, the turn ending (below), the chat's rules changing (E6), or the tab closing: bypass off, Fetch off, interception off, WebAuthn off, every registration dropped, detach if it attached. Every path goes through one `release()` (C3: never left bypassed).
- **The turn ending** (`finishTurn`, which cancels the chat's cards today): the lease's tail and after-window **outlive the turn**, since the page may still send what the last action set off; a send card the tail raises after the turn shows in the chat as its own card (*After the assistant clicked “Raise”, the page is sending something to game.example.*) and is answered as any. Your input ends it (F2).
- **Nothing** is attached, enabled or registered in a tab the assistant never acts in.

### The cards (inline in the chat's `ApprovalCard`)

- **The site card**: *Let the assistant click and type on game.example?* · *It wants to click “Raise”.* · *It asks before anything it does sends data, and before it submits, pays, sends or deletes.* · **No** · **Allow for this chat** · **Always on this site**.
- **The risky-step card** (every time): *Place the order on shop.example?* · *The assistant is about to click “Place order · $48.20”.* · *Goes with it: Shipping, Card, Gift note* · **Allow** (red for paying and deleting) · **Don't** · **Show me**.

## Risk from context (for agents and the assistant; the owner, 2026-11-24: in M2g)

*The owner, 2026-11-24: "the simple words are a kinda silly way to do it. Knowing the context of what site someone is on is probably more useful."* Words misfire both ways: *Raise* is a payment at a real-money table and a game move elsewhere; *Continue* on a checkout pays. What Chord can know of context, and how far to trust each:

1. **Structure (strong, kept, can't be faked into *safer*).** What the page can't hide without breaking itself: a payment-card field (`autocomplete=cc-*`, forms' payment rules), a frame from a payment processor (a short list in core: the card frames of the big processors, by origin), a password or one-time-code field in the form, a form that posts to another origin, an address that deletes or signs out, a DELETE, and the effect layer (what an action actually sends). These ask, as today.
2. **Site context Chord observed itself (medium, local only).** Chord can remember, per registrable domain and on this computer only, what it has seen there: card fields or a processor's frame (*this site takes payments*), a saved card or address used there, a password saved for it. A step on a site that takes payments, in a form or flow that reaches checkout structure (a cart, an order summary with a total), counts as *pay* even when the button says *Continue*. Nothing is looked up remotely (no site categories from a server: that would tell a server where you act), and nothing the page says about itself counts.
3. **Your choice per site (strong, yours).** On a site card and in Settings: *Real money on this site?* **Ask about payments** (the default) · **No real money here** (the card game). *No real money here* turns off the pay **words** there, never structure: a card field or a processor's frame still asks. Kept with *Always on this site*, listed and removable.
4. **A model's judgment (escalation only).** The acting model declares, on each action, what it expects the step to do (`expects`: `nothing`, `sends`, `pays`, `deletes`, `signs_out`, `posts`). Anything but `nothing` asks the matching card; `nothing` lowers nothing. A fooled model can only add a card, never remove one. It costs no extra call. A separate judging model, seeing the page in context, isn't proposed: it adds a call's delay to every action, and page text reaches it as it reaches the actor, so it can't be trusted to lower risk either; its only use would be adding cards the structure misses, measured first.
5. **Words (weak, narrowed).** Kept for what structure can't see: *delete*, *sign out*, *send* and *post* (in a text area's form), and the pay words where no site choice says *no real money*. Matched on the control's own short label (≤ 4 words), not anywhere in long text, so *All in one* or *Show all in folder* never match. Their weight: they ask, but a site's *No real money here* switches off the pay words alone.

**Settled (the owner, 2026-11-24):** structure plus observed site context plus your per-site choice plus the model's escalation-only `expects`, with words narrowed to short labels. It changes `control-risk.ts`, which agents and the assistant share, so it's built in **M2g, for both callers**, after M2e-2 ships on M2d's classifier as it is (plus answer 3). Before building, measure on fixtures how many steps each layer catches and how many cards it costs (the method M2d used for the send hold).

## M2e-2a: as built (2026-11-24)

**What's held, and for how long** (Claude's S3, round 2 of #150): what the page *sends* is held and asked about during an action and 1.5 s after it (`TAIL_MS`), never longer. M2e-2b's 6 s window (`AFTER_MS`) catches what the click *sets off* (pickers, passkeys, popups, downloads, the clipboard, the service worker); it doesn't hold sends past the 1.5 s. So a send card still up after the tail holds only what it named: a later send to the same site, past the tail, goes out while that card waits. Your key or click in the tab during an action or its tail ends *Allow for this chat* there (F1); after the tail it doesn't.

**What a tab of yours pays for the typing guard** (invariant 9; `agent-guard.perf.test.ts` in `pnpm test:perf`, with budgets of 2 ms and 5 µs): installing it, dormant, in the top frame of every http(s) tab of yours, takes a median of 0.007 to 0.010 ms; each key the page gets costs 0.18 to 0.22 µs with it against 0.13 to 0.15 µs without (Node's `EventTarget`, Windows x64 here, three runs). Its listeners return at once while it's down.

**Stated limits** (the reviews of #147; none needs a fix before the flag flips, each is said here and, where the user would see it, in the chat):

- **The typing guard is in the top frame only.** A frame's page that moves the focus during the assistant's typing isn't stopped by it; the focus check before each input (C3) and the frame's sends held by the lease still are.
- **What outlives the lease's tail** (`TAIL_MS`, 1.5 s, or as long as a card waits): a worker's or a `BroadcastChannel`'s message to another tab, a `keepalive` request or a beacon started inside the tail and sent after it. Each is the page's own, after the assistant's step; M2e-2b's 6 s window narrows it.
- **WebSocket and WebRTC:** a socket open before the action carries what the page sends on it, unheld (the Fetch domain never sees its frames). The step's own risk card (submit, pay, send, delete) still asks first.
- **`window.print()`** blocks the page's renderer (the spike): the action's page calls time out, the action says so, and nothing prints without you.
- **A renderer crash mid-action:** the lease is lost (B3), what was held fails, and the action says so; what the crashed page had already sent is gone with it.
- **A frame's copy** (M2e-2b; the final check of #150): `execCommand('copy')` in a frame writes the clipboard, and the page's top frame (the only one of your tabs with Chord's preload) sees no copy event. It's never put back: the chat says *The clipboard changed while the assistant acted; check it before you paste*.
- **Shared workers** (M2e-2b): a shared worker is the site's, shared with your other tabs there; the lease attaches dedicated workers only, so what a shared worker sends during the lease isn't held. What the page hands it (a message) is no request the hold sees.
- **A debugger detaching mid-lease** (your DevTools taking the tab): Chromium lets go of the requests it had paused, so they go on. The lease is lost at once, nothing more is pressed or typed, and the action says so.
- **A slow cancelled action can hold a newer lease's tail** (Neon, the final pass on #147): each action's end is its own, and a chat's are ended oldest first, so a newer action's end can wait behind an older, cancelled one still unwinding. It fails closed (the lease stays on, what the page sends stays held and asked about), and your key, click or page move still lets go of it at once.

## Stale-ref re-resolution (the owner's bug #2, pulled forward from M2g, 2026-11-24)

The owner, on a web game whose table redraws every second (a turn timer): every click and key on its buttons came back *That element changed since the snapshot*, even right after a snapshot. The buttons look the same; their DOM nodes are replaced. A ref names a node (kept by a WeakRef); a node replaced is a node gone.

**What changes:** when a ref's node is gone (collected, or no longer in the document), the action looks for it again in the page as it is now: an element with the same role, the same name, the same place in the tree (its ancestors' tags and roles), and the same shape where risk lives (its tag and type, its link's address, its form's address and method, a button's own `formaction` and `formmethod`), shown, in the same document (never a frame). Exactly one such element: the ref is that element from then on, everything after is checked on it as on any element (describe, the step, the card, the step again before input, the hit test), and the result says the ref was found again. None, or more than one: the same refusal as before (*That element changed since the snapshot*). A node that's still there but changed (another name or role) is never looked for again: it's that element, changed.

**Threat checklist** (what a hostile page can do by swapping elements):
- *A different button under the same name* (Fold becomes Buy chips, or a *Continue* whose form now posts elsewhere): its name, link address, form address or method differ, so it isn't the element; refused. A risky step's card is built from what's found, and the step is described again right before input (stepShape): a swap between the card and the click is refused (*The page changed what that step would do*).
- *The same name, place and shape, another script behind it*: not seen by any check. It's no new power: a page can change what a node it never replaced does at any time (its own listeners), and that was so before. What it sends is held (the send hold), and what its words say is classified.
- *Duplicates* (the owner's bug #5: two buttons named alike in the same place): more than one match, refused, never a guess. A page can put a decoy beside a button to make it refuse: it only stops the agent, as a covering element does.
- *A field that's now a password field, or a file input*: describe's checks refuse it, as for any element.
- *Hidden or off-screen copies*: only a shown element counts (the snapshot's own rule); the hit test still refuses one that's covered.
- *Another frame*: never looked in (the snapshot doesn't list frames' contents: M2g).
- *A huge page, to make the search slow*: the search is capped by elements looked at and by time (as the snapshot is); past either, refused.
- *Re-resolution as a way round staleness*: only for a node gone; another page (a navigation) makes every ref stale as before (the snapshot's token and page id), and the agent never gets a new outline from it: it's one element, found or not.

**As built (feat/s18-stale-refs).** The snapshot keeps, with each ref, its place (`refPath`: up to 16 ancestors' tags and roles, out through open shadow roots) and its shape (`refShape`: tag, type, link address, form address and method, `formaction`, `formmethod`). An action whose ref's node is gone looks once through the document and its open shadow roots (act.ts: at most SNAPSHOT_SCAN elements and REFIND_MS, 50 ms) for shown elements with that role, name, place and shape, stopping at a second; exactly one, and the ref is bound to it for the rest of the action and after. Every step of the action goes through it (tools.ts' `actOn`), so a step that finds it again (the first, or the check before input after a card) says so, and the result carries *The page had redrawn that element; Chord found it again by its role, name, place and target.* Measured (the Linux container, X11): the point step on an element the page replaced with a copy, found again 30 times of 30, median 3.6 ms on the typical page (1,500 elements) and 4.6 ms on /noisy, against 0.6 ms for one still there. *Tests:* agents.spec's *a table that redraws its buttons* (every 300 ms: Fold and Call found again, by click and Enter; a risky Delete row whose card names it, redrawn while the card is up, clicked once on Allow; two Bets in one place refused; Raise inside a form that buys, refused, nothing sent); the budgets journey reports the re-find timing.

**Review of #117 (Claude and Neon), re-finding narrowed.**
- *Only where it's safe*: an action finds a replaced node again only at its first look (`describe` with `refind`), the look after a card, the pointer's move (`point`) and the hit test (which checks the element at the point is ours). Never once the element is checked and pointed at: the step checked again before input, the focus, the text and a value, a choice, the values remembered (a no there now stops the input). A replacement then refuses, so a press can't land at the old point on a twin, and a field can't turn sensitive between the check and the text.
- *The closed-root check is on the same node*: deep.ts' `open()` looks the ref's element up again each time (connected, or stale), never the one from when its session opened.
- *Only what was unique*: a ref is findable again only if nothing in its snapshot shared its role, name, place and shape, and only from a snapshot that wasn't cut short (refs, elements or time). Two Deletes, one per row: neither is ever found again (failed before: the row-one ref was found as row two's).
- *The shape is the target's*, read as riskOf reads it (`actTarget`, `closestDeep` shared): its tag, type and id (a label's `for`), its link's address (`a` or `area`, across shadow roots), its form's address and method, its own `formaction` and `formmethod` where it has them (as resolved), `autocomplete`, `name`, `placeholder`, disabled, read-only, and its words where an aria-label says otherwise. The place is JSON (a role's words can't pass for an ancestor), up to the root (64).

## #143: a step's sends past the call's deadline (as built, #266)

- **The deadline.** An outside agent's call answers within `CALL_WAIT_MS` (50 s from its start), under every client's own limit: Codex's `tool_timeout_sec` (60 s by default), Antigravity's 3 minutes, and Claude Code's move of a call still running after 2 minutes to a background task (the *MCP task … failed* the owner saw).
- **The hand-over** (`control/handed-over.ts`). A step's Send data cards come after its input. When one is really up at the deadline (the gate listed it), or opens after it, once the input is done and the step wasn't refused or stopped, the call answers the step's usual result with `sending` (*What the page is sending waits for the user on Chord's card: don't repeat this step. Its outcome comes with your next result.*) and `loading: true`, never waiting for the page's load or its diff. The cards go on, unchanged for the user (their own 45 s, Allow, Don't).
- **While it waits** the tab is in `sendsWaiting`: another action there is refused (`sendsPending`); other tabs, and reading this one, go on.
- **One exit, `settle`.** Allow, a partial Allow, Don't, no answer, too many sites, the tab closed (the live store), Stop, the user taking the tab (or Keep on it), the agent's session ending (`chords.done` fails what its tabs hold), or the page committing another document while something's held. It drops what wasn't allowed, takes the card down, ends the watch, clears `sendsWaiting`, and records one entry, `{tab_id, tool, step, went, why}` in the past tense, for the agent's **next** result (`later`, inside the untrusted envelope: `step` is the page's words), never the answer that handed over. A refusal after the hand-over withdraws it, entry and all.
- **Past the deadline with no card up and nothing held**, the call answers then (`loading: true`); what the page sends after is the tab's, asked between actions.
- **navigate and back** check, before handing over, what an answer would (Stop, the user's hand, the hold, a page that can't be read); a card's Allow counts only while the page is the document it was when the card opened (`movedOn`). A batch stops at a step that hands over (`sending`, `stopped_after`).
